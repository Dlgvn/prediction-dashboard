  <name>Task 1: Package legitimacy gate — verify `arch` before install</name>

  </read_first>
  <what-built>
    Nothing installed yet. RESEARCH.md's Package Legitimacy Audit flagged `arch==8.0.0` as
    [SUS] — slopcheck's name-similarity heuristic fires on the edit distance between "arch"
    and "torch". The researcher's assessment is that this is a false positive: `arch` is
    Kevin Sheppard's (bashtage, University of Oxford) volatility-modelling library, ~10 years
    old, with a continuous version history back to 1.0 and no registry-abuse signal. Per
    project protocol, [SUS] packages get a blocking human verification before install,
    regardless of the researcher's assessment.
  </what-built>
  <how-to-verify>
    1. Open https://pypi.org/project/arch/ — confirm the project description is
       "ARCH and other tools for financial econometrics", the latest version is 8.x, and the
       release history goes back years (not a burst of recent releases).
    2. Confirm the "Homepage"/"Source" link points to https://github.com/bashtage/arch.
    3. Open that GitHub repo — confirm the owner `bashtage` also owns `linearmodels`, the repo
       has multi-year commit history, and it is not a fork/mirror created recently.
    4. Confirm the maintainer listed on PyPI matches the GitHub owner.
    5. If anything looks off (recent-only releases, mismatched repo, unknown maintainer),
       reject — the documented fallback is to skip `arch` entirely and use ARIMA/SARIMAX
       native forecast standard errors (which grow with horizon) as the volatility source,
       which plan 02-04 already produces.
  </how-to-verify>

    - On rejection, Task 2 is skipped and the executor records "GARCH not pursued — arch install

    Create `backend_research/requirements-research.txt` pinning the research-phase-only
    dependencies, kept deliberately separate from the shipped app's requirements per STACK.md's

    requirements unless a Phase 3 decision explicitly re-adopts them. Then run
    `pip install -r backend_research/requirements-research.txt`.

    Create `backend_research/run_garch.py`:
    - `fit_garch(returns)`: `arch_model(returns, vol="Garch", p=1, q=1, mean="Constant",
      dist="normal").fit(disp="off")`. Per Assumption A4, GARCH(1,1) only — do not sweep
      EGARCH/GJR variants; the sample is too small to support them and D-01 specifies GARCH generically.
    - Input must be PERCENT RETURNS: `series.pct_change().dropna() * 100`, consistent with the
      pct-change framing already used in causality_matrix.py and model_harness.py. GARCH models
      the conditional variance of returns, not price levels.
    - `garch_horizon_sigma(res, horizon=12)`: read
      `res.forecast(horizon=horizon, reindex=False).variance.values[-1]`, take the elementwise
      square root to get per-horizon sigma in percent, and return a list of 12 floats. Assert the
      sequence is non-decreasing within floating tolerance; if it is NOT non-decreasing, record
      `"widening": false` in the output — PITFALLS.md requires spreads that widen with horizon,
      so a non-widening GARCH result is a red flag that must surface in the report, not be smoothed over.
    - Pitfall 3 handling — convergence must be explicit per series: capture
      `res.convergence_flag` and any optimizer warnings via `warnings.catch_warnings(record=True)`.
      Record per series: `converged` (bool), `convergence_flag`, `warnings` (list of strings),
      `n_returns`. If a fit raises or fails to converge, record
      `"viable": false, "fallback": "arima_forecast_se"` and CONTINUE to the next series — a
      GARCH failure on hdan/ppan's shorter history is a valid, reportable research finding per
      RESEARCH.md, not a task failure.
    - Also compute a rolling-origin sanity check using the shared harness's origin logic is NOT
      required here (GARCH forecasts variance, not levels); instead refit GARCH at three origins
      (last observation, minus 12 months, minus 24 months) and record whether the horizon-1 sigma
      is stable across them. Flag `"stable_across_origins": false` if the three horizon-1 sigmas
      differ by more than 50% relative to their median.
    - Run for all four db_loader.TARGETS. Write
      `backend_research/results/garch_volatility.json` (indent=2) keyed by series name, and print
      a per-series line: series, n_returns, converged, sigma at h=1 / h=6 / h=12, viable.
  </action>
