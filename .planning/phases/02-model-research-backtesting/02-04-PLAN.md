  <action>
    Create `backend_research/run_baseline_ets.py` producing records in the <interfaces> shape,
    using `walk_forward_backtest` from the shared harness for every model — no bespoke loops.

    Four model specs, all fitted on price LEVELS (not pct change) so forecasts are directly
    comparable in MAPE terms:
    1. `NaiveForecaster` (family "baseline"): a tiny class whose `.forecast(steps)` returns the
       last training value repeated `steps` times — the random-walk benchmark. This is the number
       Pitfall 4 requires ML to be judged against.
    2. `MovingAverageForecaster(window=3)` (family "baseline"): `.forecast(steps)` returns the
       mean of the last 3 training observations repeated.
    3. SES: `statsmodels.tsa.holtwinters.SimpleExpSmoothing(train_y).fit()`.
    4. Holt with damped trend: `ExponentialSmoothing(train_y, trend="add", seasonal=None,
       damped_trend=True).fit()`. Per RESEARCH.md Pattern 4, do NOT enable a seasonal component —
       there are fewer than two clean annual cycles for some series and PITFALLS.md warns against
       seasonal terms in that regime. Record this exclusion in the record's `notes` field.

    Both 1 and 2 have `horizon_strategy: "iterative"` by construction (a flat forecast is the
    degenerate iterative case); SES and Holt likewise use statsmodels' native multi-step forecast.
    No direct variant is needed for this family — state that in `notes` rather than omitting it.

    Harness parameters: `min_train=36, horizon=12, step=1, refit_every=1` (these models are cheap
    enough to refit every origin). Wrap each fit with try/except and let the harness's
    failed-origins bookkeeping carry through into the record.

    For every spec also call `single_holdout_mape(...)` and store it, so the D-07 comparability
    number sits alongside the walk-forward numbers.

    Guard against NaN gaps: run each series through `.dropna()` before backtesting and record the
    resulting `n` in `notes` — some predictors/targets start later than others.

    Write all records to `backend_research/results/wf_baseline_ets.json` (indent=2) and print a
    table of series × model × mape at h=1, h=6, h=12.

  <action>
    Create `backend_research/run_arima_sarimax_wf.py`. Reuse the manual `itertools.product`
    grid-search style already validated in `run_sarimax_tuned.py` — do NOT add `pmdarima`, which
    STACK.md explicitly rules out as anything beyond optional research convenience.

    ARIMA (family "arima", horizon_strategy "iterative"):
    - Order grid p ∈ {0,1,2}, d ∈ {0,1}, q ∈ {0,1,2} = 18 combos per series.
    - Select the winning order ONCE per series on the first `min_train=36` window by AIC, then
      hold that order fixed for the whole walk-forward run. Fixing the order up front is the
      Pitfall 2 cost control AND mirrors how Phase 3 will ship a hard-coded order rather than
      re-searching at runtime (STACK.md's explicit anti-auto_arima guidance). Record the chosen
      order in `model` and the AIC in `notes`.
    - `fit_arima(train_y, train_x)` returns
      `statsmodels.tsa.arima.model.ARIMA(train_y, order=chosen).fit()`; pass it to
      `walk_forward_backtest` as fit_fn.

    SARIMAX with exog (family "sarimax", horizon_strategy "iterative"):
    - Exogenous predictors come from `shortlist_for(target, tier="p10")` — never from intuition.
      If the shortlist is empty (expected possibility for fx_rate per Pitfall 5), skip SARIMAX for
      that series and record a single record with `"notes": "no predictor passed the causality
      screen at p<0.10; AR-only ARIMA is the honest specification for this series"` and null MAPEs.
      Do NOT lower the threshold to manufacture a predictor.
    - CRITICAL leakage rule (RESEARCH.md Pitfall 1): the exog frame handed to the harness must be
      the SHIFTED predictor, i.e. `exog[p] = history[p].shift(lag)` for the lag the screen chose,
      so the value used at forecast time was already observable at the origin date. Never feed a
      predictor's contemporaneous or future actual value — that would test an unrealisable
      "we know the future predictor" scenario.
    - Use the same fixed order chosen for ARIMA, with `enforce_stationarity=False,
      enforce_invertibility=False` to avoid optimizer failures on short windows.

    Direct multi-step variant (family "sarimax", horizon_strategy "direct") per D-06:
    - `direct_ols_multistep(train_df, target_col, feature_cols, h)`: build `target_h =
      y.shift(-h)`, features = the shifted causality-selected predictors plus y's own lags 1-3,
      fit `statsmodels.api.OLS` with a constant, dropna. Fit 12 separate models, one per horizon.
    - Evaluate this under the same rolling origins as the iterative runs so the comparison is
      like-for-like: at each origin, refit all 12 direct models on data up to that origin only,
      and predict each horizon once. Implement this by calling `walk_forward_backtest` with a
      fit_fn whose returned object's `.forecast(steps)` internally dispatches to the h-th direct
      model — that keeps ALL window slicing inside the shared harness, which is the single
      anti-leakage rule of this phase.
    - Note in `notes` that direct models lose h rows of training data per horizon, which matters
      most for the shortest series.

    Cost control per Pitfall 2: use `refit_every=1` for ARIMA/SARIMAX if a full run finishes in
    under ~10 minutes; otherwise raise to 3 and record the cadence in `refit_every`. Never silently
    change it — the value in the record is the documentation.

    Also record `single_holdout_mape` for every spec for D-07 comparability, and print a
    stdout comparison against backend_research/REPORT.md's prior numbers (HDAN 9.4%, PPAN 10.0%,
    Diesel-USD 3.4%, FX 0.25%). Per Pitfall 1, if any walk-forward MAPE comes in dramatically
    BETTER than those figures, print a loud "LEAKAGE SUSPECT" warning line rather than celebrating.

    Write everything to `backend_research/results/wf_arima_sarimax.json` (indent=2).
  </action>
