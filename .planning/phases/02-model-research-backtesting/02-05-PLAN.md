  <action>
    Create `backend_research/run_var_vecm_wf.py`.

    `build_var_system(target)`: returns the ordered list of column names entering the VAR —
    the target first, then up to 3 predictors taken from `shortlist_for(target, tier="p10")` in
    ascending-p order. Cap at 4 endogenous series total. This cap is a degrees-of-freedom
    constraint, not a modelling preference: RESEARCH.md notes a VAR on 4 series needs ~20-30
    observations before the first origin to avoid degenerate fits, and PITFALLS.md flags
    small-sample overfitting as this project's core risk. Record the cap rationale in `notes`.
    Additionally, always include `ppan` in hdan's system and `hdan` in ppan's system per D-04's
    explicit "the other AN product's lagged value for VAR" instruction, even if the screen did
    not surface it — and note that forced inclusion in the record.

    Fit on percent changes (`pct_change_frame`) for stationarity, consistent with
    run_var_candidates.py's existing framing, then convert forecasts back to price levels for
    MAPE: `level_forecast[h] = last_observed_level * prod(1 + pct_forecast[:h]/100)`. Put this
    reconstruction inside the fit_fn's returned wrapper object's `.forecast(steps)` so the shared
    harness still compares levels to levels and does all the window slicing.

    `fit_var(train_df)`: `statsmodels.tsa.api.VAR(train_df).fit(maxlags=3, ic="aic")`. Select
    maxlags once on the first training window and hold the selected lag order fixed across origins
    (same rationale as the ARIMA order fixing in plan 02-04: Pitfall 2 cost control plus parity
    with how Phase 3 will ship a fixed specification). Record the chosen lag order in `model`.

    Run `walk_forward_backtest` with `min_train=48, horizon=12, step=1`. Use `refit_every=1` if a
    full run completes in under ~10 minutes; otherwise `refit_every=3`, and record the actual value.
    `min_train=48` (higher than the univariate family's 36) is the RESEARCH.md-mandated guard
    against degenerate multivariate fits at early origins — do not lower it to gain origins.

    horizon_strategy is "iterative" (VAR's native multi-step is recursive by construction). Add a
    "direct" counterpart for this family by reusing plan 02-04's `direct_ols_multistep` approach
    with the VAR system's members as features — import it from `run_arima_sarimax_wf` rather than
    reimplementing, so D-06's comparison exists for this family too.

    Also record `single_holdout_mape` per spec and print a stdout comparison line against
    backend_research/REPORT.md's prior VAR figures (HDAN 9.49%, PPAN 10.08%), flagging
    "LEAKAGE SUSPECT" if the walk-forward number is dramatically better.

    Write all records to `backend_research/results/wf_var_vecm.json` (indent=2).

  <action>
    Extend `run_var_vecm_wf.py` with `fit_vecm(train_df, coint_rank)` using
    `statsmodels.tsa.vector_ar.vecm.VECM(train_df, k_ar_diff=1, coint_rank=coint_rank,
    deterministic="ci").fit()`, forecasting via `.predict(steps=h)`.

    Scope: fit VECM ONLY for systems whose members appear in `VECM_CANDIDATES` from plan 02-02.
    Determine `coint_rank` with
    `statsmodels.tsa.vector_ar.vecm.select_coint_rank(train_df, det_order=0, k_ar_diff=1)` on the
    first training window and hold it fixed across origins.

    Critical framing difference from Task 1: VECM is fitted on LEVELS, not percent changes —
    the whole point of an error-correction model is the long-run level relationship. So the fit_fn
    wrapper for VECM must NOT do the pct-to-level reconstruction Task 1 needs; `.predict()` already
    returns levels. Getting this backwards silently produces nonsense MAPE — assert in the wrapper
    that the forecast magnitude is within 10x of the last observed level and raise otherwise.

    Same harness parameters as Task 1 (`min_train=48, horizon=12`), `family: "vecm"`,
    `horizon_strategy: "iterative"`.

    If `VECM_CANDIDATES` is empty, do NOT skip silently: write one record per series with
    `"family": "vecm"`, null MAPEs and
    `"notes": "no cointegrating relationship found at p<0.05 in the Engle-Granger sweep; VECM not
    applicable — plain VAR on differences is the correct specification"`. That negative result is
    a required finding for the report, not an absence.

    Append these records to the same `results/wf_var_vecm.json` file written in Task 1.
  </action>
