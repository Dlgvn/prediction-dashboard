Key format: `f"{row.date}:{attr}"`. The single draft row always has `date == ""`, so its
keys look like ":hdan" / ":date" — unambiguous against persisted rows, whose dates are
non-empty ISO strings. `key.split(":", 1)` yields ("", "hdan") for a draft cell.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser event -> DashboardState event handler | All cell values, target row dates and delete targets are client-supplied and must be re-validated server-side |
| DashboardState -> SQLite | The only write path in the application |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-04 | Tampering | commit_edit | mitigate | Validation runs inside the event handler (server-side Python) before any `session.add`; there is no client-only validation layer to bypass (RESEARCH anti-pattern "Validating only client-side") |
| T-04-05 | Tampering | commit_edit column argument | mitigate | The column name is taken from `editing_key` and used with `setattr` on a typed SQLModel field; an unknown column would raise rather than silently write — write only reaches columns declared on PriceRow |
| T-04-06 | Denial of Service | add_row | mitigate | `add_row` is a no-op while a draft exists (D-06b), so repeated client calls cannot grow `draft_rows` unbounded |
| T-04-07 | Repudiation | request_delete | accept | Single-user local tool per PROJECT.md; no audit log required. The two-click arm/confirm (D-07) is the accidental-deletion control |
| T-04-08 | Tampering | SQL layer | accept | ORM `setattr`/`session.delete` only; no raw SQL string construction anywhere in this plan |
</threat_model>
