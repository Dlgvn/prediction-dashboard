resets `self.edit_error = ""` unconditionally on every call, which can silently wipe a

def start_edit(self, key: str, current: str | float | None) -> None:
    self.editing_key = key
    if current is None or current == "":
        self.draft_value = ""
    else:

    self.cancel_edit()

        return
    row_date, column = self.editing_key.split(":", 1)

        self._commit_draft_cell(column)
        return

        ok, value, error = validate_date(
            self.draft_value, [r.date for r in self.rows], own_original_date=row_date,
        )
        if not ok:
            self.edit_error = error   # editing_key is NOT cleared on failure

    self.editing_key = ""
    self.draft_value = ""

**Key invariant (already true today, do not break):** on validation failure, neither
`commit_edit` nor `_commit_draft_cell` touch `editing_key` — the failing cell stays "open."
`edit_error` is therefore only ever meaningful while `self.editing_key` still equals the key
that produced it. `_editable_cell` in `app.py` only renders the error `rx.text` inside the
branch gated by `rx.cond(DashboardState.editing_key == key, editor, display)` — so once
`editing_key` changes to a different cell, the old error can never render again regardless of
whether `edit_error` itself is cleared.

**The race:** browser blur-then-click ordering (or Reflex event batching) can deliver
`commit_edit()` (sets `edit_error`, leaves `editing_key` unchanged) immediately followed by
`start_edit(new_key, ...)` for a *different* cell, before the error-bearing render is ever
visible. `start_edit`'s unconditional `self.edit_error = ""` plus `self.editing_key = new_key`
means the error is gone and the editor has already moved on — the user never perceives it.

From app/app/csv_import.py + app/app/state.py (D-03 audit surface):
`import_error` is set only inside `handle_csv_upload` (on a fresh upload) and cleared only by
`_reset_import()`, called from `handle_csv_upload` (start), `cancel_import`, and
`dismiss_import` — all explicit, single-shot user actions. There is no analogue of
`start_edit`'s "open a different thing mid-flight" trigger that can clobber `import_error`
before it renders; `import_error` and `edit_error` are also structurally independent fields
(Phase 10 deliberately did not merge them). Confirm this by reading the call sites; do not
assume — grep every assignment to `import_error` and `import_stage` and confirm none of them
can fire as a side effect of an in-progress *edit* interaction.
