# Phase 15 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope Note

This phase is an interaction/behavior fix, not a new-surface design phase. Per
15-CONTEXT.md D-01/D-02, it swaps the existing free-text date `rx.input` inside
`_editable_cell` (app/app/app.py) for a native `rx.input(type="date")`, and fixes an
error-clobber race in `start_edit` (app/app/state.py). No new colors, spacing tokens,
typography, copy strings, or components are introduced. All values below are
pre-populated verbatim from the existing design system (`app/app/theme.py`, locked in
Phase 6/11) and from 15-CONTEXT.md decisions — nothing new was asked of the user for
this phase.

## Color

Reused as-is from `app/app/theme.py` `LIGHT`/`DARK` dicts (mode-resolved via
`tokens(mode)`, per Phase 11). No new colors introduced.

| Role | Value (light / dark) | Usage |
|------|-------|-------|
| Dominant (60%) | `PAGE_BG` #FAFAFA / #18181B | Page canvas |
| Secondary (30%) | `SURFACE` #FFFFFF / #27272A | Table/card surface |
| Accent (10%) | `ACCENT` #2563EB / #60A5FA | Not touched by this phase — no accent-colored element is added |
| Destructive/Error | `DESTRUCTIVE` #DC2626 / #F87171 | Inline validation error text under the date cell (existing `color_scheme="red"` on the error `rx.text`); also the existing red `border_color` on the input while `edit_error != ""` |

Accent reserved for: unchanged from Phase 6 contract (buttons, active nav tab, links)
— this phase does not add or remove any accent usage.

Color behavior fix (not a new token): the existing red border/red error-text pairing on
`_editable_cell` must continue to appear reliably for the one remaining error case this
phase leaves in place — `DATE_DUPLICATE_ERROR` (malformed-format errors become
structurally impossible once `type="date"` is used, per D-02). The bug being fixed is
that `start_edit` currently clears `edit_error` unconditionally, sometimes racing away a
genuinely-set error before the user can see it. The visual treatment itself does not
change.

## Copywriting Contract

No new copy is introduced. Existing strings are reused verbatim; this phase's job is to
make the existing error text (`validators.DATE_DUPLICATE_ERROR`) reliably visible, not
to reword it.

| Element | Copy |
|---------|------|
| Primary CTA (unchanged) | "Add row" (existing `add_row` button, not touched this phase) |
| Date cell empty/placeholder | Native `rx.input(type="date")` browser-default placeholder (`mm/dd/yyyy` or locale equivalent) — no app-authored placeholder string; do not add custom placeholder text, per D-01/D-02's "no format-guessing" intent |
| Error state (duplicate month) | Existing `validators.DATE_DUPLICATE_ERROR` string, rendered via the existing inline red `rx.text` under the cell — reused verbatim, not reworded |
| Error state (invalid/incomplete date) | Structurally eliminated by `type="date"` per D-02 — the browser either returns a valid ISO date or an empty string; no malformed-value error copy is needed or should be added |
| Destructive confirmation (unchanged) | Existing two-click delete: icon button -> "Confirm delete?" (`_delete_cell`, not touched this phase) |

## Interaction Contract (phase-specific — supplements standard template sections)

| Behavior | Contract |
|----------|----------|
| Date cell — draft row (add new row) | `rx.input(type="date")` bound through the existing `_editable_cell(row, attr="date")` / `draft_value` / `update_draft` / `_commit_draft_cell` path (D-01). No new component, no duplicated cell renderer. |
| Date cell — edit existing row | Same `rx.input(type="date")` swap, same shared `_editable_cell`, through `editing_key` / `commit_edit`'s `column == "date"` branch (D-01). Both paths must go through one shared date-input branch inside `_editable_cell`, not two parallel implementations. |
| Non-date columns | Unchanged — keep the existing free-text `rx.input` (no `type="date"`) for every other attribute in `_COLUMNS`. |
| Value format on change/commit | ISO `YYYY-MM-DD` string emitted natively by the browser's `type="date"` control — no client-side format parsing or adapter unless Reflex 0.9.8's `rx.input(type="date")` API is confirmed at implementation time to require one (Claude's Discretion per CONTEXT.md — verify against installed Reflex docs before coding). |
| Error visibility | `edit_error` (existing single scalar) continues to render via the existing `rx.cond(DashboardState.edit_error != "", rx.text(...), rx.fragment())` block already in `_editable_cell`. No new error field, no new error component. |
| Error timing fix | `start_edit` must stop unconditionally resetting `edit_error = ""`; the reset must not race away a genuinely-set `DATE_DUPLICATE_ERROR` from a near-simultaneous edit-session close. No visual change — purely a state-transition timing fix (full transition table to be written during planning per PITFALLS.md). |
| Windowing / CSV import interaction | Must not regress — `toggle_show_all_history`'s existing `cancel_edit()`/`cancel_pending_delete()` calls remain the precedent; the date-picker swap and race fix must not orphan an in-progress edit when windowing is toggled. No new UI needed to satisfy this — it's a regression-test requirement, not a design requirement. |
| Min/max date range | None — no artificial range restriction on the native picker unless a clear reason emerges during planning (CONTEXT.md discretion note); duplicate-month check already guards data integrity. |
| CSV import date errors (D-03, conditional) | If the audit finds the same race-class bug in `csv_import.py`'s separate `import_error` plumbing and the fix is small, apply the same non-visual timing fix there — `import_error` stays its own separate scalar (established in Phase 10, not merged with `edit_error`). No new copy or visual treatment. If it needs a real UX redesign, defer to a future phase per CONTEXT.md — do not improvise a new picker/format affordance for bulk CSV rows in this phase. |
